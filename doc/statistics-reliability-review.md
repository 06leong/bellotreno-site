# 历史统计可靠性审查 — 2026-09-06

## 功能目的与数据边界

BelloTreno 的实时查询回答某一列车或车站“现在怎样”。上游实时接口不是永久
历史数据库，所以另设采集、稳定化和归档链路，保留以后无法再次查询到的运营
证据。历史页面用这些证据回答准点率、延误分布、运营商与类别构成、车站和线路
差异、时段规律，以及某次具体服务的延误变化。

这不是全网官方报告。缺失采集、未完成行程、身份不明确、跨日服务、取消、没有
终到延误必须保留各自含义。不能把缺失记为零，也不能为了节省内存平均每日
分位数来代替窗口内的精确分位数。

```mermaid
flowchart LR
    upstream[铁路实时接口] --> collector[常驻采集服务]
    collector --> live[SQLite operational data]
    live --> snapshot[独立一致性快照与 ready receipt]
    snapshot --> archive[离线增量 Parquet 归档]
    archive --> manifests[不可变分区与完成清单]
    manifests --> compute[离线 DuckDB 语义计算]
    compute --> export[分批导出 SQLite]
    export --> indexes[独立 SQLite 索引进程]
    indexes --> publish[校验后原子发布 read model]
    publish --> api[常驻只读 Analytics API]
    api --> pages[Cloudflare Pages Function]
    pages --> dashboard[历史页面与延迟加载 ECharts]
```

本次审查跟踪了 `PROJECT_GUIDE.md`、analytics roadmap、VPS README、Compose、
systemd 日任务、快照/归档/语义构建、只读 API、Pages Function、前端状态及
normalizer。主页查询、车站面板和其他铁路提供方仍走各自的实时数据链路；
它们不承担历史分析计算。Cloudflare 部署成功只证明网站部署成功，不能证明
离线 Analytics 容器构建成功。

## 资源问题为什么反复出现

| 边界 | 已发现的问题 | 当前处理 |
| --- | --- | --- |
| 事实表 | 当天停站关联累计全部服务；大历史一次物化 | 两侧按服务日约束；工作库落磁盘、逐批 checkpoint |
| 输入文件 | 每个日期批次重新绑定全部历史文件，历史越长开销越大 | 一次读取 Parquet 的真实服务日期范围；按批次选择文件，缺失范围时保守保留 |
| 观察记录 | 文件按采集日分区，不能用目录日期判断服务日 | 按 Parquet 列统计筛选，保留跨采集日的同一服务观察 |
| 窗口与排名 | 多窗口、多筛选、宽行排名同时占用工作内存 | 固定窗口/筛选批次；排名先保留服务身份，再回取详情 |
| 车站图表 | 对同一停站历史重复扫描、哈希数百次 | 将最多 180 天的一个精简车站分片落磁盘，复用于全部比较窗口 |
| SQLite 导出 | Python fetch 分批不能约束 DuckDB 已物化结果 | SQL 查询本身限制为 5,000 个物理行范围 |
| SQLite 索引 | 默认排序临时文件写进很小的 `/tmp`；运行中修改环境太晚 | DuckDB 关闭后启动独立索引进程，进程启动前设置磁盘临时目录 |
| 发布失败 | 中途失败或进程被杀可能留下工作文件 | 发布锁、旧库保留、原子替换；下次在锁内清理废弃工作目录 |

SQLite 的 Unix 实现在初始化期间读取临时目录环境变量，见
[SQLite 源码](https://sqlite.org/src/artifact/410185df49)。上一轮 scoped
`os.environ` 修改没有覆盖这个生命周期，因此 CI 33970345088 仍在同一个索引
失败。现在索引进程从启动时就获得正确环境，不依赖父进程是否已初始化 SQLite，
也不使用已弃用的全局 `temp_store_directory` PRAGMA。

## 长期运行的实际范围

- 永久数据是 Parquet 与完成清单；SQLite read model 可丢弃重建。
- 公共语义层默认保留 730 天的计算历史。7/28/90 天窗口不被缩短。
  车站/线路最新图表只需要当前与上一周期，共最多 180 天。
- 一天内的数据量、单个站点的样本量仍会影响峰值；分批不代表任何数据规模下
  内存都恒定。现在分别测试高密度历史与两年日期/分区增长。
- DuckDB `128MB` 是缓冲预算；容器 `384 MiB` 才是总内存限制，包含原生分配、
  Python 和文件缓存等。索引进程计入同一个容器限额。
- DuckDB 的 `4GB` 只限制其 spill，工作库、新旧 SQLite、索引排序还需要磁盘。
  增量归档已有容量预检；真实 VPS 的剩余磁盘仍必须纳入受控构建记录。
- 每日任务的 900 秒安全窗口只是启动条件，不能保证一个超过 15 分钟的计算
  与下一轮采集不重叠。不能以此宣称整台 VPS 不会 OOM。
- 生产 VPS 可用内存约 907 MiB，采集容器与分析容器的上限相加超过物理内存。
  CI 的单容器通过不等于整个生产主机通过。应在实际归档上记录采集期间的
  `MemAvailable`、Swap、OOM、构建时间和 API build ID，再恢复定时器。
- 若实际日任务逐渐超过可用窗口或磁盘预算，下一步是有版本和来源校验的增量
  语义缓存，或在第二台 VPS 计算后发布读模型。不能通过无限增加内存限额、
  删除永久归档、减少指标或隐瞒失败来维持表面成功。

## 验收与故障证据

1. 快速 Linux 回归：同进程排序在 16 MiB `/tmp` 上确实产生 `SQLITE_FULL`；
   相同 40 万行由新索引进程成功处理并清理临时目录。
2. 完整密集回归：90 天、72 万服务、864 万停站，真实 archive 镜像，
   384 MiB、无额外 Swap、单 CPU、只读根目录和归档。
3. 长日期回归：730 天、每日 100 服务，在相同容器限制下检查窗口、总数、
   全部 14 张表、SQLite 完整性和工作目录清理。这不是两年全密度基准。
4. 小样本逐表等价：所有 14 张表双向 SQL EXCEPT 与行数一致；覆盖跨采集日
   观察、上一周期、取消、空值和服务身份；保留失败前旧库字节。
5. 仓库检查、生产构建、Compose 解析和每日任务场景通过。
6. main 对应镜像发布后，由维护者在真实 VPS 执行升级及受控构建。测试未完成
   前保持每日定时器停用；不把本地或 CI 数据冒充生产数据。

上面是验收要求，执行结果以对应 CI 和受控 VPS 日志为准；任何未执行的步骤
不能写成已通过。
